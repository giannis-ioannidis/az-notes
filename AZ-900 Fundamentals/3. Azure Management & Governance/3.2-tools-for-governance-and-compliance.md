# 3.2 Governance & Compliance

## Azure Policy

### Definition
Azure Policy is a service that enables you to create, assign, and manage policies that enforce rules and effects over your resources to ensure they stay compliant with corporate standards and service level agreements.

### Purpose
- **Enforce standards**: Ensure resources comply with organizational rules
- **Assess compliance**: Identify non-compliant resources
- **Remediate**: Automatically fix non-compliant resources
- **Prevent violations**: Block creation of non-compliant resources

---

### Key Concepts

#### Policy Definition

##### What It Is
A rule that defines what to check and what action to take.

##### Structure
```json
{
  "if": {
    "condition": "Resource doesn't meet requirement"
  },
  "then": {
    "effect": "Action to take"
  }
}
```

##### Examples of Policy Definitions
- Allowed virtual machine sizes
- Allowed locations for resources
- Require tag on resources
- Require secure transfer for storage accounts
- Allowed resource types

---

#### Policy Effects

##### Append
- **Action**: Adds additional fields to resource
- **Use case**: Add specific tags automatically
- **Example**: Append "Environment: Production" tag to all VMs

##### Deny
- **Action**: Prevents resource creation/update
- **Use case**: Block non-compliant resources
- **Example**: Deny VM creation in non-approved regions

##### Audit
- **Action**: Creates warning in activity log, allows creation
- **Use case**: Identify non-compliant resources without blocking
- **Example**: Log when VMs created without backup enabled

##### AuditIfNotExists
- **Action**: Checks if related resource exists, logs if not
- **Use case**: Verify configurations that depend on other resources
- **Example**: Audit VMs that don't have antimalware extension

##### DeployIfNotExists
- **Action**: Automatically deploys related resource if missing
- **Use case**: Auto-remediate compliance issues
- **Example**: Deploy diagnostic settings if not configured

##### Modify
- **Action**: Adds, updates, or removes tags on resources
- **Use case**: Tag governance and management
- **Example**: Update "Owner" tag based on resource group

##### Disabled
- **Action**: Policy exists but is not evaluated
- **Use case**: Temporarily turn off policy without deleting

---

#### Policy Assignment

##### Definition
Applying a policy definition to a specific scope (management group, subscription, or resource group).

##### Scope Hierarchy
```
Management Group (broadest)
  └── Subscription
      └── Resource Group
          └── Resource (narrowest)
```

##### Inheritance
- Policies assigned at higher scope apply to all child scopes
- Resource in resource group inherits policies from:
  - Resource group
  - Subscription
  - Management group

##### Example Assignment
```
Policy: "Allowed locations"
Scope: Production subscription
Parameters: East US, West US only

Result: All resources in Production subscription 
        can only be created in East US or West US
```

---

#### Initiative (Policy Set)

##### Definition
A collection of policy definitions grouped together to achieve a specific compliance goal.

##### Purpose
- Group related policies
- Simplify management
- Apply multiple policies at once

##### Built-in Initiative Examples

###### CIS Microsoft Azure Foundations Benchmark

###### NIST SP 800-53 R4

#### Remediation

##### Purpose
Fix non-compliant resources automatically or on-demand.

##### Remediation Types

###### Automatic Remediation (DeployIfNotExists, Modify)
```
Policy: Deploy diagnostic settings
Effect: DeployIfNotExists

When: New storage account created without diagnostics
Action: Automatically deploy diagnostic settings
Result: All storage accounts have diagnostics
```

###### Manual Remediation Tasks
```
Policy: Require specific tag
Effect: Audit
Non-compliant: 50 resources missing tag

Action: Create remediation task
1. Policy identifies 50 resources
2. Administrator reviews
3. Clicks "Remediate"
4. Policy applies fix to all 50 resources
```

##### Remediation Example
```
Scenario: 100 VMs don't have required tags

Steps:
1. Policy → Compliance → Select policy
2. View non-compliant resources (100 VMs)
3. Click "Create Remediation Task"
4. Configure:
   - Re-evaluate compliance: Yes
   - Managed identity: System-assigned
5. Submit
6. Monitor progress
7. Result: All 100 VMs now have required tags
```

### Built-in vs Custom Policies

#### Built-in Policies
- **Count**: 300+ policies available
- **Maintained**: By Microsoft, automatically updated
- **Categories**: Security, cost, compliance, operations
- **Ready to use**: No development needed
- **Examples**:
  - Allowed locations
  - Allowed resource types
  - Require tag
  - Audit VMs without managed disks

#### Custom Policies
- **Creation**: Define your own rules using JSON
- **Use case**: Organization-specific requirements
- **Flexibility**: Complete control over logic
- **Example**:
```json
{
  "if": {
    "allOf": [
      {
        "field": "type",
        "equals": "Microsoft.Compute/virtualMachines"
      },
      {
        "field": "location",
        "equals": "eastus"
      }
    ]
  },
  "then": {
    "effect": "deny"
  }
}
```

### Policy Best Practices

#### 1. Start with Audit Effect
```
Initial deployment:
Effect: Audit (don't block, just report)

After reviewing compliance:
Effect: Deny (enforce compliance)

Reason: Understand impact before enforcing
```

#### 2. Use Initiatives for Related Policies
```
Instead of: Assigning 20 individual policies
Use: One initiative containing all 20 policies

Benefit: Easier management, single assignment
```

#### 3. Test in Non-Production First
```
1. Assign to Dev/Test subscription
2. Monitor compliance
3. Address issues
4. Roll out to Production

Reason: Prevent business disruption
```

#### 4. Leverage Built-in Policies
```
Before creating custom policy:
1. Check built-in policies
2. Check Azure Policy samples on GitHub
3. Create custom only if needed

Reason: Built-in policies are tested and maintained
```

#### 5. Document Policy Decisions
```
For each policy assignment, document:
- Business justification
- Scope and exclusions
- Remediation plan
- Review schedule

Reason: Compliance audits and governance
```

### Definition
Microsoft Purview is a unified data governance service that helps organizations manage and govern their data across on-premises, multi-cloud, and SaaS environments.

### Purpose
- **Data discovery**: Find and catalog data across your estate

## Resource Locks

### Definition
Resource locks prevent accidental deletion or modification of critical Azure resources by blocking operations at the resource, resource group, or subscription level.

### Purpose
- **Prevent accidents**: Stop accidental deletion
- **Protect production**: Safeguard critical resources
- **Governance**: Enforce change management
- **Compliance**: Meet regulatory requirements

---

### Lock Types

#### CanNotDelete Lock

##### Description
Users can read and modify resource, but cannot delete it.

##### What's Allowed
- ✅ Read resource properties
- ✅ Modify configurations
- ✅ Add/remove tags
- ✅ Change settings

##### What's Blocked
- ❌ Delete the resource
- ❌ Delete resource group containing it

##### Use Case
```
Scenario: Production SQL Database
Lock type: CanNotDelete

Result:
- DBAs can modify database (scale, configure)
- Database cannot be accidentally deleted
- Requires lock removal before deletion

Protection: Prevents accidental deletion during cleanup
```

---

#### ReadOnly Lock

##### Description
Users can read resource but cannot modify or delete it.

##### What's Allowed
- ✅ Read resource properties
- ✅ View configurations
- ✅ Monitor and view logs

##### What's Blocked
- ❌ Modify any settings
- ❌ Change configurations
- ❌ Add/remove tags
- ❌ Delete the resource
- ❌ Start/stop operations

##### Use Case
```
Scenario: Production Virtual Network
Lock type: ReadOnly

Result:
- Network engineers can view configuration
- Cannot modify subnets, IP ranges, or security rules
- Prevents configuration drift
- Requires lock removal for changes

Protection: Ensures network stability, change control process required
```

---

### Lock Scope

#### Resource Level
```
Lock on: Single VM

Effect:
- Only that specific VM is locked
- Other resources unaffected
- Most granular control
```

#### Resource Group Level
```
Lock on: Production-RG

Effect:
- All resources in resource group locked
- Inherited by all current and future resources
- Simplified management (one lock protects many resources)
```

#### Subscription Level
```
Lock on: Production Subscription

Effect:
- All resource groups locked
- All resources in subscription locked
- Broadest protection
- Use carefully (very restrictive)
```

---

### Lock Inheritance

#### How Inheritance Works
```
Subscription (ReadOnly lock)
  └── Resource Group (inherits ReadOnly)
      └── Virtual Machine (inherits ReadOnly)
      └── Storage Account (inherits ReadOnly)

Result: Cannot modify ANY resource in subscription
```

#### Most Restrictive Lock Wins
```
Resource Group: CanNotDelete lock
Resource: ReadOnly lock

Result: Resource has ReadOnly (more restrictive)

Rule: Most restrictive lock in hierarchy applies
```

---

### Managing Locks

#### Creating Locks

##### Azure Portal
```
1. Navigate to resource
2. Click "Locks" in left menu
3. Click "+ Add"
4. Name: Production-Protection
5. Lock type: CanNotDelete or ReadOnly
6. Notes: "Protect production database"
7. Click OK
```

##### PowerShell
```powershell
# CanNotDelete lock on resource
New-AzResourceLock `
  -LockName "DoNotDelete" `
  -LockLevel CanNotDelete `
  -ResourceName "myVM" `
  -ResourceType "Microsoft.Compute/virtualMachines" `
  -ResourceGroupName "Production-RG"

# ReadOnly lock on resource group
New-AzResourceLock `
  -LockName "ReadOnlyLock" `
  -LockLevel ReadOnly `
  -ResourceGroupName "Production-RG"
```

##### Azure CLI
```bash
# CanNotDelete lock
az lock create \
  --name DoNotDelete \
  --lock-type CanNotDelete \
  --resource-group Production-RG \
  --resource-name myVM \
  --resource-type Microsoft.Compute/virtualMachines

# ReadOnly lock on subscription
az lock create \
  --name ReadOnlyLock \
  --lock-type ReadOnly
```

---

#### Removing Locks

##### Process
```
1. Navigate to locked resource
2. Click "Locks"
3. Select lock
4. Click "Delete"
5. Confirm deletion

Requirement: Must have lock delete permissions
```

##### Who Can Delete Locks
- **Owner role**: Full permissions including locks
- **User Access Administrator**: Can manage locks
- **Custom role**: With Microsoft.Authorization/locks/delete permission

##### Lock Removal Required For
```
Scenario: Need to delete production database

Steps:
1. Submit change request (change management)
2. Get approval
3. Remove CanNotDelete lock
4. Delete database
5. (Optionally) Recreate lock on new resource

Protection: Forces deliberate process, prevents accidents
```

---

### Lock Best Practices

#### 1. Lock Critical Resources
```
Always lock:
- Production databases
- Virtual networks
- Key vaults
- Core infrastructure

Reason: Prevent accidental deletion/modification
```

#### 2. Use Resource Group Locks
```
Instead of: Locking 50 individual resources
Use: One lock on resource group

Benefit: Simpler management, consistent protection
```

#### 3. Document Lock Purpose
```
Lock name: Production-Database-Protection
Notes: "Locked per security policy SEC-001. 
        Requires change request to modify.
        Contact: dbadmin@company.com"

Benefit: Team understands why lock exists
```

#### 4. Implement Change Management
```
Process for locked resources:
1. Submit change request
2. Get approval
3. Remove lock temporarily
4. Make change
5. Reapply lock
6. Document in change log

Benefit: Controlled changes, audit trail
```

#### 5. Regular Lock Audits
```
Quarterly review:
- Are all critical resources locked?
- Are locks still appropriate?
- Update lock documentation
- Remove unnecessary locks

Benefit: Maintain effective protection
```

### Locks vs RBAC

#### Comparison

| Aspect | Resource Locks | RBAC |
|--------|---------------|------|
| **Purpose** | Prevent operations | Control who can do what |
| **Scope** | Specific operations (delete, modify) | All operations |
| **Applies to** | All users (even admins) | Specific users/groups |
| **Granularity** | Resource/Resource Group/Subscription | Action level |
| **Override** | Remove lock to proceed | Cannot override permissions |

#### Use Both Together
```
Example: Production database

RBAC:
- DBA Group: Contributor role
- Dev Team: Reader role

Lock:
- Type: CanNotDelete
- Scope: Database resource

Result:
- DBAs can modify (RBAC allows)
- DBAs cannot delete (Lock prevents)
- Devs can view only (RBAC limits)
- Devs cannot delete (Lock prevents)

Combined protection: Role-based access + deletion prevention
```

## Summary

### Azure Policy
- **Purpose**: Enforce compliance with organizational standards
- **Policy Definition**: Rules about what's allowed/required
- **Effects**: Deny, Audit, Append, DeployIfNotExists, Modify, Disabled
- **Initiative**: Group of related policies
- **Compliance**: Dashboard showing compliant vs non-compliant resources
- **Remediation**: Fix non-compliant resources automatically or on-demand

### Microsoft Purview
- **Purpose**: Unified data governance across entire data estate
- **Data Discovery**: Find and catalog data assets
- **Classification**: Automatically identify sensitive data (PII, financial, etc.)
- **Lineage**: Track data flow and transformations
- **Compliance**: Support for GDPR, HIPAA, CCPA, SOX
- **Use cases**: Cloud migration, compliance, shadow IT discovery

### Resource Locks
- **Purpose**: Prevent accidental deletion or modification
- **CanNotDelete**: Can modify but not delete
- **ReadOnly**: Cannot modify or delete
- **Scope**: Resource, resource group, or subscription
- **Inheritance**: Child resources inherit parent locks
- **Best practice**: Lock critical production resources

### Service Trust Portal
- **Purpose**: Access to Microsoft compliance information
- **Content**: Audit reports (SOC, ISO), compliance guides, blueprints
- **Audience**: Compliance teams, auditors, legal, security
- **Access**: Free with Microsoft account
- **Use cases**: Audit preparation, RFP responses, compliance assessment

### Key Takeaways
- **Azure Policy**: Preventive control (enforce before deployment)
- **Purview**: Discovery and visibility (understand what you have)
- **Resource Locks**: Protective control (prevent accidents)
- **Service Trust Portal**: Evidence and documentation (prove compliance)
- **Together**: Comprehensive governance and compliance framework
