# 3.3 Managing & Deploying Azure Resources

## Interacting with Azure

### Overview
Azure provides multiple tools and interfaces to create, manage, and monitor resources. Each tool is designed for different scenarios and user preferences.

## Azure Portal

### Definition
Web-based, unified console that provides a graphical user interface (GUI) for managing Azure resources through a web browser.

### Access
- **URL**: https://portal.azure.com
- **Requirements**: Internet browser, Azure account
- **Supported browsers**: Chrome, Edge, Firefox, Safari

### Key Features

#### Dashboard
- **Customizable**: Create personalized views
- **Tiles**: Add resource tiles, charts, metrics
- **Multiple dashboards**: Different views for different roles
- **Share dashboards**: Export and share with team

#### Resource Management
- **Visual interface**: Point-and-click resource creation
- **Blade navigation**: Side panels for context and details
- **Search**: Quick access to resources (Ctrl+/)
- **Favorites**: Pin frequently used services

#### Cloud Shell Integration
- **Built-in terminal**: Access PowerShell or Bash from browser
- **No installation**: Works without local tools
- **Persistent storage**: Files stored in Azure Storage
- **Pre-configured**: Azure CLI and PowerShell pre-installed

#### Resource Groups
- **Visual organization**: See all resources in group
- **Bulk operations**: Manage multiple resources
- **Cost analysis**: View spending by resource group
- **Activity logs**: Audit trail of changes

---

### When to Use Azure Portal

#### Best For:
✅ **Learning**: Visual interface for understanding Azure
✅ **Quick tasks**: One-off resource creation
✅ **Exploration**: Browsing available services
✅ **Monitoring**: Viewing dashboards and metrics
✅ **Troubleshooting**: Interactive diagnostics

#### Not Ideal For:

## Azure Cloud Shell

### Definition
Browser-based command-line experience for managing Azure resources, accessible from Azure Portal or directly via shell.azure.com.

### Key Characteristics
- **Browser-based**: No local installation needed
- **Pre-authenticated**: Already signed into Azure
- **Two shells**: Bash (Linux) or PowerShell
- **Persistent storage**: Files saved in Azure Storage (~$0.25/month)
- **Pre-installed tools**: Azure CLI, PowerShell, Git, editors

### Access Methods

#### From Azure Portal
```
1. Click Cloud Shell icon (>_) in top bar
2. Choose Bash or PowerShell
3. Start typing commands
```

#### Direct Access
```
URL: https://shell.azure.com
Opens Cloud Shell in full browser window
```

#### Mobile Apps
```
Available in:
- Azure mobile app (iOS/Android)
- On-the-go management
```

---

### Cloud Shell Features

#### Persistent Storage
- **File storage**: 5 GB Azure File share
- **$HOME directory**: Files persist across sessions
- **Mounted automatically**: Available immediately
- **Cross-session**: Same files from any browser

#### Pre-installed Tools
- **Azure CLI**: `az` commands
- **Azure PowerShell**: `Az` module
- **Git**: Version control
- **Text editors**: nano, vim, code (VS Code)
- **Other tools**: kubectl, Terraform, Ansible, Node.js, Python

#### Session Management
- **Timeout**: 20 minutes of inactivity
- **Reconnect**: Resume in new session
- **Multiple sessions**: Open in different tabs
- **Session storage**: Temporary files cleared on timeout

## Azure PowerShell

### Definition
Command-line shell and scripting language built on PowerShell, designed for managing Azure resources through cmdlets (command-lets).

### Installation
- **Windows**: PowerShell Gallery
- **Linux**: PowerShell Core + Az module
- **macOS**: PowerShell Core + Az module
- **Cloud Shell**: Pre-installed

### Module Structure
```powershell
# Az module (current)
Install-Module -Name Az -AllowClobber -Scope CurrentUser

# Module groups:
Az.Compute    # VMs
Az.Storage    # Storage
Az.Network    # Networking
Az.KeyVault   # Key Vault
# ... 60+ modules
```

---

### Azure PowerShell Cmdlet Structure

#### Naming Convention
```
Verb-AzNoun

Examples:
Get-AzVM          # Get virtual machine
New-AzVM          # Create virtual machine
Remove-AzVM       # Delete virtual machine
Set-AzVM          # Modify virtual machine
Start-AzVM        # Start virtual machine
Stop-AzVM         # Stop virtual machine
```

#### Common Verbs
- **Get**: Retrieve information
- **New**: Create resource
- **Set**: Modify resource
- **Remove**: Delete resource
- **Start/Stop**: Change state
- **Update**: Update configuration

## Azure PowerShell vs Azure CLI

### Comparison Table

| Aspect | Azure PowerShell | Azure CLI |
|--------|-----------------|-----------|
| **Syntax** | Verb-Noun cmdlets | Group-subgroup-command |
| **Platform** | Windows-native, cross-platform | Truly cross-platform |
| **Output** | Objects | JSON (default) |
| **Scripting** | PowerShell scripts (.ps1) | Bash/shell scripts |
| **Learning curve** | Steeper (PowerShell concepts) | Easier (simple commands) |
| **Best for** | Windows admins, complex scripts | Linux admins, CI/CD |

### Choosing Between PowerShell and CLI

#### Use Azure PowerShell When:
- You're comfortable with PowerShell
- You need object-oriented output
- Working primarily on Windows
- Complex scripting with logic and error handling
- Need to manipulate returned objects

#### Use Azure CLI When:
- You prefer bash/shell scripting
- Working in CI/CD pipelines
- Cross-platform consistency is important
- You want simple, concise commands
- JSON output is sufficient

#### Use Both:
- Mix and match based on task
- Team has diverse skill sets
- Different tools for different scenarios

## Azure Resource Manager (ARM)

### Definition
Azure Resource Manager (ARM) is the deployment and management service for Azure. It provides a management layer that enables you to create, update, and delete resources in your Azure account.

### Purpose
- **Unified management layer**: Single entry point for all Azure operations
- **Consistent interface**: Same results via Portal, PowerShell, CLI, REST API
- **Resource organization**: Group resources logically
- **Access control**: Integrate with Azure AD and RBAC
- **Template-based deployment**: Infrastructure as Code

---

### How ARM Works

#### Request Flow
```
User/Tool (Portal, PowerShell, CLI, REST API)
    ↓
Azure Resource Manager (management layer)
    ↓ Authenticates & Authorizes
    ↓ Routes request
Resource Provider (Microsoft.Compute, Microsoft.Storage, etc.)
    ↓ Performs operation
Actual Resource (VM, Storage Account, etc.)
```

#### Example: Creating a VM
```
1. User: clicks "Create VM" in Portal
2. Portal: sends HTTPS request to ARM
3. ARM: authenticates user with Azure AD
4. ARM: checks RBAC permissions
5. ARM: validates request
6. ARM: forwards to Microsoft.Compute provider
7. Provider: creates VM
8. Provider: returns result to ARM
9. ARM: returns result to Portal
10. Portal: shows "VM created successfully"
```

---

### ARM Key Features

#### 1. Consistent Management Layer

##### Single API
All tools use same ARM API:
- Azure Portal → ARM API
- PowerShell → ARM API
- Azure CLI → ARM API
- REST API → ARM API directly

##### Result: Consistent Behavior
```
Same operation via different tools produces same result:

Portal: Create VM
PowerShell: New-AzVM
CLI: az vm create
REST: POST to ARM API

All create VM identically
```

#### 2. Resource Groups

##### Purpose
Logical containers for related resources enabling management as a unit.

##### Benefits
- **Lifecycle management**: Deploy, update, delete together
- **Access control**: Apply permissions at group level
- **Billing**: View costs per resource group
- **Organization**: Group by application, environment, or department

##### Example Structure
```
Resource Group: WebApp-Production
Contains:
- App Service (web hosting)
- Azure SQL Database (data)
- Application Insights (monitoring)
- Storage Account (static files)

Operations:
- Delete group → deletes all resources
- Apply RBAC → applies to all resources
- View costs → see total for application
```

#### 3. Resource Providers

##### Definition
Services that supply Azure resources, each handling specific resource types.

##### Common Resource Providers
- **Microsoft.Compute**: Virtual machines, VM scale sets
- **Microsoft.Storage**: Storage accounts, disks
- **Microsoft.Network**: Virtual networks, load balancers
- **Microsoft.Web**: App Services, Functions
- **Microsoft.Sql**: SQL databases, SQL servers

##### Resource Provider Registration
```powershell
# List all resource providers
Get-AzResourceProvider

# Check if registered
Get-AzResourceProvider -ProviderNamespace Microsoft.Compute

# Register provider (if needed)
Register-AzResourceProvider -ProviderNamespace Microsoft.Compute
```

##### Resource Types
```
Format: {Provider}/{ResourceType}

Examples:
Microsoft.Compute/virtualMachines
Microsoft.Storage/storageAccounts
Microsoft.Network/virtualNetworks
Microsoft.Sql/servers/databases
```

#### 4. Tags

##### Purpose
Metadata for organizing and tracking resources (covered in detail in section 3.1).

##### ARM Support
- Apply tags during resource creation
- Update tags after creation
- Inherit tags via policy
- Query resources by tags

---

#### 5. Locks

##### Purpose
Prevent accidental deletion or modification (covered in detail in section 3.2).

##### ARM Integration
- ARM enforces locks before allowing operations

#### 6. RBAC Integration

##### Purpose
Control who can perform what actions (covered in detail in section 2.4).

##### ARM Integration
```
Every ARM request checked:
1. Who is making request? (Authentication via Azure AD)
2. What are they trying to do? (Operation)
3. Are they allowed? (RBAC check)
4. Proceed or deny
```

### ARM Templates

#### Definition
JSON files that declaratively define Azure infrastructure and configuration, enabling repeatable deployments.

#### Purpose
- **Infrastructure as Code (IaC)**: Define infrastructure in code
- **Repeatable**: Deploy same environment multiple times
- **Version control**: Store templates in Git
- **Consistency**: Eliminate manual errors
- **Automation**: Integrate with CI/CD pipelines

---

### ARM Template Structure

#### Basic Template
```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {},
  "variables": {},
  "resources": [],
  "outputs": {}
}
```

#### Sections Explained

##### $schema
- Specifies template schema version
- Defines available properties

##### contentVersion
- Template version number
- Track template changes

##### parameters
- Input values provided at deployment
- Make templates reusable

##### variables
- Values used throughout template
- Simplify template maintenance

##### resources
- Azure resources to deploy
- Core of the template

##### outputs
- Values returned after deployment
- Useful for automation

---

### ARM Template Example

#### Simple Storage Account Template
```json
{
  "$schema": "https://schema.management.azure.com/schemas/2019-04-01/deploymentTemplate.json#",
  "contentVersion": "1.0.0.0",
  "parameters": {
    "storageAccountName": {
      "type": "string",
      "minLength": 3,
      "maxLength": 24,
      "metadata": {
        "description": "Storage account name"
      }
    },
    "location": {
      "type": "string",
      "defaultValue": "[resourceGroup().location]",
      "metadata": {
        "description": "Location for all resources"
      }
    }
  },
  "variables": {
    "storageSKU": "Standard_LRS"
  },
  "resources": [
    {
      "type": "Microsoft.Storage/storageAccounts",
      "apiVersion": "2021-04-01",
      "name": "[parameters('storageAccountName')]",
      "location": "[parameters('location')]",
      "sku": {
        "name": "[variables('storageSKU')]"
      },
      "kind": "StorageV2",
      "properties": {
        "supportsHttpsTrafficOnly": true
      }
    }
  ],
  "outputs": {
    "storageAccountId": {
      "type": "string",
      "value": "[resourceId('Microsoft.Storage/storageAccounts', parameters('storageAccountName'))]"
    }
  }
}
```

### Bicep (ARM Template Alternative)

#### Definition
Domain-specific language (DSL) for deploying Azure resources, providing simpler syntax than JSON ARM templates.

#### Comparison

**ARM Template (JSON):**
```json
{
  "type": "Microsoft.Storage/storageAccounts",
  "apiVersion": "2021-04-01",
  "name": "[parameters('storageAccountName')]",
  "location": "[parameters('location')]",
  "sku": {
    "name": "Standard_LRS"
  },
  "kind": "StorageV2"
}
```

**Bicep:**
```bicep
resource storageAccount 'Microsoft.Storage/storageAccounts@2021-04-01' = {
  name: storageAccountName
  location: location
  sku: {
    name: 'Standard_LRS'
  }
  kind: 'StorageV2'
}
```

#### Bicep Benefits
- **Simpler syntax**: Less verbose than JSON
- **Better tooling**: IntelliSense, validation
- **Modular**: Easy to reuse code
- **Compiles to ARM**: Same reliability
- **Free and open source**

### Template Deployment Modes

#### Incremental Mode (Default)
```
Behavior:
- Adds/updates resources in template
- Leaves existing resources unchanged
- Safe for adding resources

Example:
Resource Group has: VM1, Storage1
Template defines: VM1 (updated), VM2 (new)
Result: VM1 (updated), Storage1 (unchanged), VM2 (new)
```

#### Complete Mode
```
Behavior:
- Deploys resources in template
- DELETES resources not in template
- Dangerous - use carefully

Example:
Resource Group has: VM1, Storage1
Template defines: VM1 (updated), VM2 (new)
Result: VM1 (updated), VM2 (new), Storage1 (DELETED!)

Warning: Can cause data loss!
```

### ARM Template Best Practices

#### 1. Use Parameters for Reusability
```json
✅ Good:
"parameters": {
  "environment": {
    "type": "string",
    "allowedValues": ["dev", "test", "prod"]
  }
}

❌ Bad:
Hard-coded values in template
```

#### 2. Use Variables for Repeated Values
```json
✅ Good:
"variables": {
  "resourcePrefix": "[concat(parameters('projectName'), '-', parameters('environment'))]"
}

❌ Bad:
Repeating same concatenation multiple times
```

#### 3. Organize with Linked Templates
```
Main template (azuredeploy.json)
├── Links to: network.json
├── Links to: storage.json
└── Links to: compute.json

Benefit: Modular, reusable components
```

#### 4. Validate Before Deploying
```powershell
# PowerShell
Test-AzResourceGroupDeployment `
  -ResourceGroupName "MyRG" `
  -TemplateFile "azuredeploy.json"

# CLI
az deployment group validate \
  --resource-group MyRG \
  --template-file azuredeploy.json
```

#### 5. Use What-If to Preview Changes
```powershell
# PowerShell
New-AzResourceGroupDeployment `
  -ResourceGroupName "MyRG" `
  -TemplateFile "azuredeploy.json" `
  -WhatIf

# CLI
az deployment group what-if \
  --resource-group MyRG \
  --template-file azuredeploy.json
```

| **Mobile App** | Mobile | Monitoring on-the-go | Alerts, quick actions |
| **REST API** | Programmatic | Custom apps | Full control, integration |

### Azure Resource Manager (ARM)

**Core Concepts:**
- **Management layer**: Single entry point for all Azure operations
- **Resource groups**: Logical containers for resources
- **Resource providers**: Services that supply Azure resources
- **Consistent interface**: Portal, PowerShell, CLI all use ARM

**ARM Templates:**
- **Infrastructure as Code**: Define resources in JSON/Bicep
- **Repeatable**: Deploy identical environments multiple times
- **Version control**: Track changes in Git
- **Automation**: Integrate with CI/CD pipelines
- **Benefits**: Consistency, reproducibility, automation

**Template Structure:**
- **Parameters**: Input values for reusability
- **Variables**: Repeated values, simplify maintenance
- **Resources**: Azure resources to deploy
- **Outputs**: Values returned after deployment

### Key Takeaways
- **Multiple tools available**: Choose based on preference and scenario
- **All tools use ARM**: Consistent results regardless of tool
- **ARM templates enable IaC**: Repeatable, version-controlled infrastructure
- **Resource groups organize resources**: Lifecycle, access, billing
- **Bicep simplifies templates**: Easier to write than JSON
- **Portal for learning**, **CLI/PowerShell for automation**
